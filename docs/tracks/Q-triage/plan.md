## 2. Phases

Suggested order: **Q.1 config-loader → Q.2a relation-merge → Q.2 signals → Q.3 status-assignment + migration → Q.4 pipeline-orchestration (the after-extraction hook) → Q.5 UI**. Q.2a (relation edge-dedup + cross-doc provenance) is a PREREQUISITE for Q.2's promotion logic and must land before Q.2. Q.3 can run in parallel with Q.2/Q.2a once Q.1 lands.

> **Operator-mandated promotion model (load-bearing).** Weak `RELATED` edges are NOT excluded from connectivity — they PROMOTE. An entity that becomes increasingly connected by the SAME RELATED link recurring across documents must earn `active`. This is only securable if relations are MERGED (one edge per src+tgt+predicate, accumulating `source_documents`); the current persist DUPLICATES edges (70 live dups, each with one doc), so per-edge cross-doc recurrence is not tracked. **Phase Q.2a closes this gap** (forward edge-dedup + provenance union + a backfill of the existing dups); Q.2's degree then counts structural edges + PROMOTED weak edges (RELATED whose cross-doc count ≥ `weak_promotion_min_docs`). Config: `relation_predicates.weak_promotion_min_docs` (= 2).

### Phase Q.2a — Relation merge (edge-dedup + cross-doc provenance accumulation)

**Reuse-vs-new**: NET-NEW. This is the gap that secures the operator's promotion model; it is NOT covered by the existing persist.

**Goal**: make relations idempotent and cross-doc-aware. Today `entity_persistence_service.py` runs `RELATE $s->relation->$t SET source_documents = [$source_id]` unconditionally — so the same edge re-appearing in another document creates a DUPLICATE edge (70 live dups confirmed), and per-edge cross-doc recurrence is never accumulated. Q.2a makes one edge per `(in, out, relation_type)` whose `source_documents` is the cumulative UNION across documents/batches, so a recurring `RELATED` edge's doc-count grows and can promote (Q.2).

**Reuse anchors**:
- `entity_persistence_service.py` relation persist loop (~lines 520–595, the `RELATE ... SET source_documents = [$source_id]`) — the forward seam.
- Relation table schema (migration 58): `source_documents` array, `confidence`, `properties` already exist — NO schema change needed; only the write logic changes.
- `EntityRepository` relation helpers (`repoint_relations`, the relation SELECTs) — read the existing projections before assuming field names (spec mandate).

**Files to modify**:
- `entity_persistence_service.py` — replace the unconditional `RELATE` with an UPSERT-style edge write: look up an existing edge `(in=$s, out=$t, relation_type=$rt)`; if found, `UPDATE` it with `source_documents = array::union(source_documents, [$source_id])` (+ optionally bump a recurrence/weight + max-confidence); else `RELATE` a new edge with `source_documents = [$source_id]`. Idempotent: re-persisting the same (edge, doc) is a no-op union.

**Files to create**:
- `scripts/backfill_relation_merge.py` — collapse the existing duplicate edges: group active relations by `(in, out, relation_type)`, keep one, union their `source_documents` (+ max confidence, merge `properties` signals), delete the redundant edges. Idempotent, dry-run flag, logs collapsed count.

**Acceptance criteria**:
1. Persisting the SAME relation from two different `source_id`s yields ONE edge with `source_documents` length 2 (not two edges).
2. Re-persisting the same (edge, source_id) is a no-op (union idempotent) — `source_documents` stays length 2, no duplicate edge.
3. The backfill collapses the 70 live duplicate `(in,out,relation_type)` groups into one edge each with unioned provenance; re-running the backfill collapses nothing further (idempotent).
4. No relation is deleted that isn't a true duplicate; endpoint records and `relation_type` are preserved; O.1 type-safe endpoint resolution unaffected.
5. A weak `RELATED` edge recurring across 3 documents ends with `source_documents` length 3 — the input Q.2 promotion needs.

**Tests required**:
- Unit/integration: `test_relation_merge.py` — same-edge-two-docs → one edge len-2; idempotent re-persist; backfill collapses a seeded dup set and is idempotent; non-dups untouched.

**PR boundary**: ONE PR — `feat(triage): idempotent relation merge + cross-doc provenance + dedup backfill (Q.2a)`.

**Effort estimate**: 1.5–2 days.

### Phase Q.2 — Signals (effective degree w/ weak-edge promotion, cross-doc recurrence, affected set)

**Reuse-vs-new**: NET-NEW with partial reuse (graph_analyzer centrality optional). DEPENDS ON Q.2a (per-edge cross-doc counts must be accurate).

**Goal**: compute per-node EFFECTIVE structural degree = count of `structural` edges + count of PROMOTED weak edges (a `weak`/`RELATED` edge whose `source_documents` count ≥ `weak_promotion_min_docs`), bucketed 0 / 1–2 / 3+; cross-doc recurrence (distinct doc count from `source_documents`); and the **affected set** = new nodes + nodes whose effective-degree or doc-count changed this batch. A single-doc RELATED edge does NOT count (and is backbone-flagged in Q.4); a multi-doc RELATED edge DOES count (promoted). Only the affected set is re-triaged.

**Reuse anchors**:
- `EntityRepository` — `packages/surrealdb-service/src/surrealdb_service/repositories/entity.py`. Relation queries already exist (`repoint_relations`, the merge-planning loader reading `source_documents` at line ~640). Read predicates/endpoints from the relation table; **do not invent field names — read the schema (migration 58) and the repo's existing SELECT projections first** (spec mandate).
- `config/triage_config.json` `relation_predicates` (via Q.1 `predicate_strength`) for the structural filter.
- `pipelines/entity-filtering/src/entity_filtering/validation/graph_analyzer.py` (`GraphAnalyzer.analyze`, `_compute_centrality`) — reuse centrality where a richer connectivity signal helps; OPTIONAL, do not block on it. Note: graph_analyzer builds an in-memory `nx.DiGraph` from a batch's relations, not the persisted KG — for persisted-degree, query the relation table directly.

**Files to create**:
- `apps/app-main/src/app_main/services/triage/signals_service.py` — `TriageSignalsService`:
  - `structural_degree(entity_id) -> int` (counts relations where `predicate_strength == "structural"`, both directions, status `active`).
  - `degree_bucket(degree) -> "0"|"1-2"|"3+"`.
  - `doc_count(entity) -> int` (distinct entries in `source_documents`).
  - `compute_affected_set(batch_entity_ids, pre_batch_snapshot) -> set[id]` (new + changed-degree + changed-doc-count).
  - Returns a `SignalsReport` (dataclass: per-id degree, bucket, doc_count, is_new, changed flags).

**Files to modify**:
- `EntityRepository` (entity.py) — ADD a read-only helper IF one doesn't already exist: a batch structural-degree query `degree_for_entities(ids, structural_predicates) -> dict[id,int]` (single round-trip, not N queries). Additive method, no schema change.

**Acceptance criteria**:
1. **Promotion**: an entity with 2 `BIJDRAGT_AAN` edges + 1 `RELATED` edge that is single-doc → effective degree `2` (the single-doc RELATED does NOT count). The SAME entity once that `RELATED` edge reaches `source_documents` ≥ `weak_promotion_min_docs` (2) → effective degree `3`, bucket flips `"1-2"`→`"3+"`. This is the operator's promotion guarantee, asserted directly.
2. An entity appearing in 3 distinct `source_documents` has `doc_count == 3`; a re-run of the same batch keeps it at 3 (idempotent — no double-count). [Relies on Q.2a edge/entity provenance union.]
3. `compute_affected_set` returns exactly the new nodes plus nodes whose effective-degree or doc-count changed vs the pre-batch snapshot; unchanged nodes are excluded. (A weak edge crossing the promotion threshold this batch makes its endpoints "changed".)
4. Degree computation is one batched DB call for the affected set, not one-per-node (assert query count in test).
5. Directionality: a structural (or promoted-weak) edge counts toward both endpoints' degree.

**Tests required**:
- Unit: `test_triage_signals_service.py` with a seeded mini-KG (active edges, weak edges, multi-doc provenance) — degree buckets, doc-count dedup, affected-set membership, weak-edge exclusion.
- Integration: against the surreal test fixture, assert batched query count.

**PR boundary**: ONE PR — `feat(triage): structural-degree + recurrence signals (Q.2)`.

**Effort estimate**: 1.5–2 days.

## 3. Risk assessment (riskiest design decisions — operator confirmation requested)

- **R1 — Where the after-extraction hook fires** | The two `persist_filtered_result` call sites (`entity_extraction_service.py:1155` main path, `:1362` re-filter path) are the seam. Risk: hooking only one path misses re-filters; hooking inside the filtering try/except would swallow triage as "filtering failed". Mitigation: add a guarded post-persist call after BOTH sites, OUTSIDE the filtering try/except, with its own log-and-continue (mirror line 1141). **Confirm**: triage fires on the re-filter path too (recommended yes).
- **R2 — `manual_override`: column vs `properties` key** | Recommendation = dedicated `DEFINE FIELD manual_override ON entity TYPE bool DEFAULT false` (migration 59). Rationale: queryable/indexable, explicit in the schema the UI binds to, and immune to `properties` union-merge overwrite semantics (entity.py merges `properties`). A properties-key avoids a migration but is fragile under merge and harder to filter. **Confirm**: column route.
- **R3 — Status-change log store: table vs file** | Recommendation = `status_change_log` SurrealDB table (joinable, queryable, restart-safe, fits the migration story) over an append-only file. **Confirm**: table route. Same question applies to the triage queue (recommend `triage_queue` table; whether its migration folds into 59 or a new 60 depends on Q.3/Q.4 merge timing).
- **R4 — Affected-set snapshot correctness** | Idempotency hinges on the pre-batch snapshot used by `compute_affected_set`. Risk: if degree/doc-count is read AFTER merge, "changed" detection breaks and unchanged nodes get re-triaged (noise) or changed nodes get missed. Mitigation: capture the pre-batch snapshot before B2 merge; assert idempotency in integration test (run-twice). 
- **R5 — Named-programme typing gap** | NOVEX / Regio-Deals only reach `active` if typed `Programma`/`Deal`/`RegioDeal`; otherwise they fall to `unsure_review`. Mitigation: the review queue catches them (acceptable for v1). Documented as a known limitation + a possible later alias rule (config `entity_tiers` already lists the programme types). **Confirm**: queue-catch is acceptable for v1, alias rule deferred.
- **R6 — Relation-merge changes the persist write path (Q.2a)** | Making the edge write an UPSERT (look-up-then-union) instead of an unconditional `RELATE` touches the O.1 relation-persist seam. Risk: a regression in edge creation re-breaks the long-standing relation persistence (the KG was stuck at 3 relations before O.1). Mitigation: keep O.1's type-safe endpoint resolution untouched; the only change is "create vs union" AFTER endpoints resolve; cover with the O.1 roundtrip tests + the new same-edge-two-docs test. The backfill is separately gated (dry-run first, idempotent). **Confirm**: the promotion model is worth this write-path change (operator already mandated it).
