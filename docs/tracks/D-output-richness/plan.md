### Phase D.1b — Obsidian export — direct-write to vault-path mode

**Goal**: same export, but written directly to the user's configured `vault_path` instead of a zip. Used by the auto-pipeline path. Filesystem safety: never write outside `vault_path/vault_entities_folder`; atomic via tempdir + rename; never delete user content; preserve user-added files.

**Files to modify**:

- `apps/app-main/src/app_main/services/obsidian_export_service.py` (from D.1a):
  - Add `async def _write_to_vault(vault_path: Path, entities_folder: str, files: Dict[str, str]) -> int` — writes each `(filename, content)` to `vault_path/entities_folder/`. Returns bytes written.
  - Safety: `Path(vault_path).resolve()` must be a parent of every target write path (rejection of `..` traversal in filenames). Reject if `vault_path` is not absolute, doesn't exist, or isn't writable.
  - Atomicity: write each file via tempfile + `os.replace` (POSIX atomic rename). Failures leave the previous version intact.
  - Filenames that already exist in vault: **overwrite** is the default behavior (V1; the export is the source of truth for `<entities_folder>/`). User-curated files outside `<entities_folder>/` are never touched. (Q-D-6 confirms overwrite default.)
- `apps/app-main/src/app_main/api/routers/exports.py` — the same `POST /api/notebooks/{id}/export-obsidian` endpoint now handles `mode="vault_path"`. Returns `ExportReport` as JSON (no file body), HTTP 200 with `Content-Type: application/json`.
- `apps/app-main/src/app_main/handlers.py` — register a `@registry.register(JobType.EXPORT_OBSIDIAN)` handler that calls `ObsidianExportService.export(...)` with `mode="vault_path"`. This is the auto-pipeline entry point. Payload schema: `{notebook_id: str, filter: ExportFilter.model_dump()}`.
- `apps/app-main/tests/test_obsidian_export_service.py` — extend with:
  - vault-path happy-path (writes 3 files, returns ExportReport with correct counts).
  - vault-path rejection when path is not absolute (`/foo/../etc/passwd`).
  - vault-path rejection when target directory doesn't exist.
  - vault-path overwrite (pre-existing `.md` in the folder is replaced; user-added `.md` outside `<entities_folder>/` is untouched).
- `apps/app-main/tests/test_handlers.py` — assert `JobType.EXPORT_OBSIDIAN` handler is registered after `import app_main.handlers`.

**Acceptance criteria**:

1. `POST /api/notebooks/{id}/export-obsidian` with `{mode: "vault_path", filter: {...}}` and `Settings.vault_path` configured writes files to `<vault_path>/<vault_entities_folder>/`. Returns 200 with `ExportReport` JSON.
2. Filesystem safety: path-traversal in entity names (`canonical_name="../etc/passwd"`) is normalized by `normalize_entity_name` (already lowercases + strips punct) and the resulting filename is asserted to be a direct child of `<vault_path>/<entities_folder>/`. A test fixture with a malicious name verifies this.
3. Atomicity: forced-failure mid-write (mock filesystem error on the 2nd file) leaves the 1st file written and propagates the error; **no partial-state** in the response report. The endpoint returns 500 with `{error: ..., entities_written: 1}` so the client knows where the failure happened.
4. Auto-pipeline: `JobType.EXPORT_OBSIDIAN` payload `{notebook_id, filter}` resolves through the registered handler and writes successfully (verified via job-queue integration test).

6. Endpoint returns 400 if `mode="vault_path"` and `Settings.vault_path` is not configured.

**Tests required**:

### Phase D.3 — NetworkX 7-format export + endpoint + UI button

**Goal**: an endpoint that builds a `networkx.DiGraph` from `(entities, relations)` and serializes it in any of 7 formats: GraphML, GEXF, GML, JSON-tree, edge-list, adjacency-list, pickle. Reuses myKG's exporter shape but delegates serialization to the `networkx` library.

**Files to create**:

- `apps/app-main/src/app_main/services/networkx_export_service.py`:
  - `async def export(notebook_id: str, request: NetworkxExportRequest) -> bytes`:
    - Build a `networkx.DiGraph`: nodes carry `(canonical_name, entity_type, type_tags, primary_type, confidence, properties)` as node attributes; edges carry `(relation_type, confidence, properties)`.
    - Dispatch to the right serializer: `nx.write_graphml`, `nx.write_gexf`, `nx.write_gml`, `nx.tree_data → json.dumps`, `nx.write_edgelist`, `nx.write_adjlist`, `pickle.dumps`.
    - Each serializer writes to a `BytesIO` and returns the bytes.
  - **Important**: NetworkX serializers are NOT pickle-safe for arbitrary attribute types (lists/dicts in node-attrs break GraphML). The service pre-flattens `type_tags` → comma-joined string, `properties` → JSON-encoded string. Documented in module docstring.

- `apps/app-main/src/app_main/api/routers/exports.py` (extend):
  - `POST /api/notebooks/{id}/export-networkx` body `NetworkxExportRequest`; returns `Response` (NOT streaming — networkx writes are buffered) with `Content-Type` matching the format (`application/xml` for GraphML/GEXF, `application/json` for json-tree, `application/octet-stream` for pickle, `text/plain` for edge-list/adjacency-list/GML) and `Content-Disposition: attachment; filename="<notebook_name>.<ext>"`.
- `apps/app-main/tests/test_networkx_export_service.py` — covers: each of 7 formats produces a non-empty output that re-parses via the matching `nx.read_*` (round-trip); attribute flattening preserves data (e.g. `type_tags=["A","B"]` → `"A,B"` → re-split correctly); pickle round-trip preserves all fields; empty notebook produces a valid empty-graph in each format.

## 4. Risk assessment

**Risk 1 — Large-notebook memory blowup in Obsidian export.** A 10K-entity notebook with full `properties` bags + `provenance_chain` could push 100s of MB. The zip stream itself isn't the problem (zip-on-the-fly); the in-memory entity list returned by `list_entities_for_notebook` is. **Mitigation**: D.0's repo method must support **pagination** (`offset`, `limit`) and D.1a's writer must iterate in 500-row batches, building the wikilink-resolution dict in a first cheap pass (id → filename only, no body), then streaming per-entity body rendering. D.2's JSONL writer is naturally streaming. Q-D-1 confirms the embedding-field exclusion (`embedding` skipped in the projection because it's the largest field and useless for export). **Severity**: medium.

**Risk 2 — Vault-path filesystem permission/safety.** Writing to a user's local filesystem from a containerized backend has multiple failure modes: path doesn't exist, permission denied, path is a network mount with quirky atomicity, path-traversal in filenames. **Mitigation**: D.1b enforces `Path.resolve()` containment-check + absolute-path requirement + writable-check; uses atomic tempfile+rename for each file; documents the failure modes in the troubleshooting doc. The endpoint validates `vault_path` is configured before accepting `mode="vault_path"`. **Severity**: medium-high.

**Risk 3 — Filename collisions in Obsidian vault.** Two entities with the same `canonical_name` (or two whose `normalize_entity_name` collapse to the same string — e.g. `"OECD"` and `"oecd"`) would overwrite each other. **Mitigation**: D.1a's `_derive_filename` detects collisions and appends `-2`, `-3`, …; the wikilink-resolution dict maps `entity_id → final_filename`. Collisions are reported in the `ExportReport.metadata` so users see them. The relations layer uses entity-ids (not names) for endpoint resolution, so collision-resolved filenames don't break wikilinks. **Severity**: medium.

**Risk 4 — Q9 vocabulary stack not ready — `external_ids` always empty.** Roadmap §340 lists `external_ids` (TOOI/Crossref URIs) as a frontmatter key. Track M4's Q9 isn't done; Track D ships with an empty `external_ids: []`. **Mitigation**: single import-point pattern (`shared.utils.external_ids.resolve_external_ids`) mirrors B's name-normalizer. Q9 swap is a one-file change with no caller migration. Document the stub status in D.4's RETRO so M4 plan knows what to deliver. **Severity**: low (additive when Q9 ships).

**Risk 5 — NetworkX serializer attribute-type quirks.** GraphML and GEXF don't accept arbitrary Python types as node/edge attributes; lists and dicts break the writer. **Mitigation**: D.3's service pre-flattens `type_tags` to comma-joined string and `properties` to JSON-encoded string. Round-trip tests confirm the flatten/unflatten preserves data. Documented in module docstring + troubleshooting page. **Severity**: low (caught by round-trip tests at PR-time).

**Risk 6 — VaultSyncService ↔ ObsidianExportService write-collision.** Both touch `<vault_path>/<entities_folder>/`. VaultSyncService is read-only on startup (scans, loads dictionary) — it doesn't write. D.1b writes during export. The directional split is clean: VaultSyncService reads on startup; ObsidianExportService writes on export trigger. No race because they don't run concurrently in normal usage. **Mitigation**: document the directional split in D.1b's service docstring; if a user wants to re-sync after export, they restart the app (or trigger a manual vault scan, already in `VaultSyncService.scan_vault_entities`). **Severity**: low.

**Risk 7 — Reviewer-rejection cycle (RETRO #1).** Track B saw 47% first-attempt rejection; Track A saw 50%. Track D has 8 PRs; budget **3-4 second-attempts** into the calendar estimate. The riskiest phases for rejection: D.1a (largest surface, multiple subsystems), D.2 (streaming pattern is novel), D.1b (filesystem safety has many corner cases). **Mitigation**: pre-write golden snapshots for D.1a, force the inversion test pattern (RETRO #6) on every claimed-PASS AC; require self-review evidence (pytest exit + test name) per AC (RETRO #3). **Severity**: medium (it's the meta-process risk that will dominate calendar time).

**Risk 8 — JobType enum textual conflict with Track E.** Track E adds `JobType.RESEARCH`; Track D adds `JobType.EXPORT_OBSIDIAN`. Both modify the same 9-line block in `enums.py`. **Mitigation**: rebase on whichever lands first; the textual conflict is trivial. Coordinate by including the line range explicitly in each plan's "files to modify" so the implementer knows where to merge. **Severity**: very low.
