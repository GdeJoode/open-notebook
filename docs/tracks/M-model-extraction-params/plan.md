# Track M — Model-specific extraction parameters + failover-aware chunking — Sprint Plan

> Generated by track-planner agent on 2026-06-23

## 1. Context

- **Reference**: live failure observed 2026-06-23 — a Gemini-primary extraction run quota-failed mid-document (`RESOURCE_EXHAUSTED` on `generate_content_free_tier_requests`) and the failover chain fell back to `llama3.1:8b` local. Builds directly on Track **J** (the FailoverExecutor / ProviderCircuitBreaker / ProviderRateLimiter / RouteResolver stack).
- **Track goal**: make the **heterogeneous** entity-extraction failover chain robust — each model in the chain has a different context window (Gemini 2.5 Flash ~1M, Ollama Cloud ~32K, llama3.1:8b local 8K) and a different request budget (Gemini free ~10 req/min, NIM ~40, local unlimited). Today extraction uses **global** parameters: a fixed up-front chunking (`max_chunk_size=2000` chars at ingestion), a global `batch_size=10`, and a global `DEFAULT_CLOUD_RPM=20`. Track M makes chunk size **derive from the active model's `context_window`**, makes the RPM cap **per-provider**, threads `max_output_tokens` per-model, and — the crux — moves chunking **inside the per-document failover attempt** so each model re-chunks the document for its own context window.
- **The headline expected improvement**: a Gemini-primary run extracts a document in ~3 big chunks (exploiting 1M context, staying under the ~10 req/min cap); on Gemini quota-exhaustion the llama fallback **re-chunks the same document into ~20 small 8K-safe chunks** — no `context_window` overflow on the smaller fallback, and no rate-trip on the larger primary. Today either choice is wrong for half the chain.

### 1.2 The design (bake this in)

> **Per-MODEL config drives chunking; per-PROVIDER config drives rate. The two axes are separate and both already have homes.** Chunk size is a function of the *model's* `context_window` (a Gemini and a NIM model on the *same* provider could differ); the RPM cap is a function of the *provider's* quota (all Gemini models share Google's free-tier per-minute budget). M keeps them on the model record and the provider registry respectively.

- **Per-model context (M.1, M.3)**: the active candidate's `model.context_window` (already on the record) is the budget. Chunk packing reserves headroom for the prompt template + `max_output_tokens` + a safety margin, then packs ingestion chunks into the remaining input budget. A Gemini candidate (1M) packs ~all chunks into a few windows; a llama candidate (8K) packs ~1-2 ingestion chunks per window.
- **Per-provider rate (M.2)**: `per_provider_rpm = {"google": 10, "nvidia": 40, "ollama": <unlimited>}` wired into the existing `ProviderRateLimiter`. Pacing (block+backoff) is already the behaviour — M tunes the cap so the window itself respects Gemini's ~10/min instead of issuing ~20 and absorbing 429s.
- **Failover-aware re-chunking (M.4, the crux)**: each model in the chain re-chunks the document for ITS context window. Gemini attempt = a few big windows; on Gemini failure, the llama attempt re-packs into many small windows. This is the core architectural change because today chunking is once-upfront + failover is per-call.
- **`max_output_tokens` (M.1)**: already threaded by the factory; M pins it per chain-model and regression-tests the threading for all providers so the NIM-truncation class can't recur.

### Phase M.3 — Chunk size derived from the active model's `context_window`

**Goal**: stop using a model-agnostic fixed chunk grouping. Derive the extraction-time chunk **packing** from the active candidate's `model.context_window`, reserving headroom for the prompt template + `max_output_tokens` + a safety margin. A Gemini candidate (1M) packs many ingestion chunks into a few large windows; a llama candidate (8K) packs ~1 ingestion chunk per window. **This phase wires the derivation for a SINGLE (head) candidate; M.4 makes it re-derive per failover attempt.**

**Files to create**:
- `apps/app-main/src/app_main/services/extraction_chunking/__init__.py`
- `apps/app-main/src/app_main/services/extraction_chunking/context_packer.py`:
  - `pack_chunks_for_model(chunks: list[dict], *, context_window: int, max_output_tokens: int, prompt_overhead_tokens: int, safety_margin: float = 0.85) -> list[dict]` — packs the persisted ingestion chunks (each ≤2000 chars) into model-sized windows: `input_budget = int((context_window - max_output_tokens - prompt_overhead_tokens) * safety_margin)`; greedily concatenate ingestion chunks (preserving order + structural metadata) until the next chunk would exceed `input_budget` (token-estimated via a char→token heuristic, ~4 chars/token, or a real tokenizer if available). Returns the re-grouped chunk dicts (concatenated `text`, merged `section_path`/`id` provenance list).
  - `estimate_tokens(text: str) -> int` — char/token heuristic (documented, conservative-rounding-up).
  - A hard **per-window cap** so a single oversized ingestion chunk that alone exceeds `input_budget` is **re-split** (never silently overflow) — this guard is the seed of M.4's oversized-chunk handling.
- `apps/app-main/tests/test_context_packer.py`.

**Files to modify**:
- `apps/app-main/src/app_main/services/entity_extraction_service.py` (~line 917-980) — after building `chunk_dicts` and resolving the route, **pack `chunk_dicts` for the HEAD candidate's `context_window`** before `workflow.extract` / `_run_multi_schema`. Thread the active `model.context_window`/`max_output_tokens` from the resolved route's head candidate (`route.ordered_candidates[0].model`). When the head model has a null `context_window` (unseeded), fall back to the current fixed grouping (degrade gracefully).
- `pipelines/ontology-extraction/src/ontology_extraction/config.py` — document that `batch_size` is a concurrency knob (unchanged) and that effective chunk grouping is now context-derived upstream; no behavioural change to `batch_size` itself.

**Acceptance criteria** (falsifiable):
1. `pack_chunks_for_model(chunks, context_window=1_000_000, max_output_tokens=8192, prompt_overhead_tokens=2000)` over 60 ingestion chunks (~2000 chars each) returns a **small** number of large windows (e.g. ≤5), each within the input budget.
2. The same chunks with `context_window=8192` (llama) return **many** small windows, each whose estimated tokens ≤ `input_budget` (no window exceeds llama's 8K).
3. A single oversized ingestion chunk (e.g. a 40K-char table) with `context_window=8192` is **re-split** into ≥2 windows, none exceeding the budget (no silent overflow — falsifiable: assert max window token-estimate ≤ budget).
4. Packing **preserves order** and carries structural metadata (`section_path`, `physical_page`, `source_id`) and a provenance list of constituent ingestion `chunk_id`s on each window.
5. With a null-`context_window` head model, `entity_extraction_service` falls back to the pre-M grouping (graceful degrade — no crash, asserted).
6. **L coordination**: `applicable_schemas` still reaches `_run_multi_schema`/persist after packing (re-grouping is orthogonal to the document-level schema list — asserted by an L-threading regression test).
7. **B.8 shape**: the extraction-output entity/relation dataclass fields are unchanged for a fixed input under packed vs unpacked chunks (the dedup layer absorbs chunk-boundary differences — asserted on a small fixture).

**Tests required**:
- Unit (`test_context_packer.py`): large-context → few windows; small-context → many bounded windows; oversized-chunk re-split; order + metadata + provenance preservation; null-context fallback.

**Effort estimate**: **2–2.5 days**. Reviewer cycle budget: ×1.5 (new packer + a hot-path edit in the shared extraction service).

### Phase M.4 — Failover-aware per-document re-chunking (the crux)

**Goal**: 🔴 the core architectural change. Today chunking is **once-upfront** (M.3 made it head-candidate-sized) and failover is **per-LLM-call**. M.4 makes the chunking **re-derive per failover attempt**: each candidate the executor tries re-packs the document for ITS OWN `context_window`. A Gemini attempt runs ~3 big windows; on Gemini exhaustion the llama attempt re-packs the SAME document into ~20 small windows — no overflow on the smaller fallback, no rate-trip on the larger primary.

**Files to create**:
- `apps/app-main/src/app_main/services/extraction_chunking/failover_aware_extractor.py`:
  - `async extract_document_with_failover(document_chunks, route, *, packer, extract_window) -> ExtractionResult` — walks `route.ordered_candidates`; **for each candidate, calls `packer.pack_chunks_for_model(document_chunks, context_window=candidate.model.context_window, …)` to RE-PACK**, then runs the candidate's windows through `extract_window` (the per-window LLM call, rate-limited via the existing executor for that candidate), aggregating entities/relations. On a failover-eligible failure for the whole candidate (all-windows-failed OR a quota-trip), advance to the next candidate and **re-pack for it**. Reuses the J circuit-breaker + rate-limiter per candidate.
- `apps/app-main/tests/test_failover_aware_extractor.py`.

**Files to modify**:
- `apps/app-main/src/app_main/services/entity_extraction_service.py` — route the extraction through `extract_document_with_failover` so the document (not the individual pre-sized chunk) is the failover unit, and each candidate re-chunks. **This is the move from per-call to per-document failover at the chunking boundary.** Preserve the `_FailoverLLMCaller` for the per-window calls within a candidate (each window is still rate-limited/backed-off by the J executor for that candidate's provider).
- `apps/app-main/src/app_main/services/model_routing/failover_executor.py` — **extend, do not break**: the per-window call within a candidate keeps using `execute_with_failover` OR a candidate-pinned variant; the document-level walk lives in the new extractor. Decision M-D3 governs whether this is a full re-architecture (a) or the interim oversized-chunk guard (b).
- `docs/tracks/M-model-extraction-params/` — record the re-chunk behaviour + the chosen M-D3 shape.

**Acceptance criteria** (falsifiable):
1. With a route `[google(1M), llama(8K)]` and a 60-chunk document, the google attempt packs into a **small** window count (≤5) and the llama attempt (on google failure) re-packs into a **large** window count (≥15) — asserted on the per-candidate packing record. **The same document, re-chunked per candidate.**
2. **No overflow on fallback**: in the google→llama failover, **no window sent to llama exceeds llama's 8K `context_window`** (assert max llama-window token-estimate ≤ llama input budget) — the live overflow bug is closed.
3. **No rate-trip on primary**: the google attempt issues a number of LLM calls bounded by its big-window count (≤~5), staying under the google ~10/min cap — asserted that the google attempt does NOT exceed the cap for a single document (the live quota-trip cause is closed).
4. A mid-attempt google quota-trip (simulated `RateLimitError` past backoff) advances the WHOLE document to llama and **re-packs** (not: flips only the remaining google-sized chunks to llama — the today-behaviour that overflows).
5. **Aggregation correctness**: the aggregated entity/relation set from the served candidate equals the per-window union (no dropped windows, dedup applied) — B.8 output shape unchanged.
6. **J contract**: per-candidate the circuit-breaker + rate-limiter still fire (a breaker-open candidate is skipped, a 429 backs off) — the J executor semantics are reused, not bypassed (asserted).
7. **L contract**: `applicable_schemas` threads through every candidate's re-pack (document-level schemas unchanged across re-chunks) — asserted.
8. Idempotent / deterministic packing: the same document + same candidate context produces the same windows across runs (asserted for test stability).

**Tests required**:
- Unit (`test_failover_aware_extractor.py`): per-candidate re-pack window counts; no-overflow on the small fallback; quota-trip → whole-document re-pack; aggregation union; breaker/rate-limiter reuse; schema threading.
- Integration (with fakes for the LLM call): the google→llama failover end-to-end re-chunk (full simulation, deferred to M.5 with the real chain).

**PR boundary**: ONE PR titled `feat(extraction): failover-aware per-document re-chunking — each candidate re-chunks for its context (M.4)`.

**Effort estimate**: **2.5–3 days**. Reviewer cycle budget: ×2.0 (the crux — re-architects the chunking/failover boundary on the shared extraction hot path; the no-overflow/no-rate-trip ACs are the gate).

**Risks**: 🔴 (a) **the central architectural risk** — moving failover from per-call to per-document changes the blast radius of a single chunk failure (today one bad chunk fails over just itself; M.4 re-runs the whole document on the next candidate, re-doing already-succeeded windows). Mitigation: only re-pack+re-run on a CANDIDATE-level fault (quota/breaker), not a single transient window error; document the trade-off (re-work vs correctness). **Decision M-D3** explicitly offers the interim **(b) oversized-chunk guard** — keep per-call failover but re-split any chunk that exceeds the *current* candidate's context before the call — as a lower-risk V1 that closes the overflow bug without the full re-architecture. (b) re-running succeeded windows on failover wastes the primary's work — accept for V1 (correctness > efficiency); a future optimization caches per-window results. (c) the per-window-within-candidate calls still need their own rate-limiting — reuse the J executor per candidate, don't reinvent.
