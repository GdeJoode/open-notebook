## 1. Context

- **Reference**: `claudedocs/entity-typing-analysis.md` (the full analysis over the live KG: 2,357 active entities, the Regio-Deal / Dutch-gov corpus). Triggered by the K.7b finding that `VRO` and `minister van VRO` were both typed `other`, defeating the K resolution `(name, type)` guard.
- **Track goal**: stop the persistence layer from **flattening** the rich Dutch ontology types the LLM correctly emits (`Gemeente`, `Ministerie`, `RegioDeal`, `Wet`, `BeleidsThema`…) onto a fixed 20-type generic enum that dumps 27% into `other` and leaves `primary_type`/`type_tags` empty. Bridge the ontology's own **declared `parent_type` chain** → a small fixed schema.org-base → canonical-enum map (language-agnostic by construction), and **preserve the original ontology type** in `primary_type`/`type_tags` so the rich type survives. Coarse `entity_type` becomes the canonical projection for dedup/filter/the K `(name,type)` guard.
- **The headline expected improvement**: the **27% `other`** bucket collapses to near-zero (every `other` row today carries a `raw_entity_type` that IS a valid ontology type — `RegioDeal`, `Gemeente`, `Ministerie`, … — so the bridge re-types it deterministically), and the **44% generic `concept`/`topic`** drops once `policy_themes` is actually applied (L.4). Target: **`other` 27% → <5%**; **% entities with a non-null `primary_type` 0% → >90%** over the gov/policy corpus.

### 1.1 The architectural fact this track turns on (verified by reading)

> **The system fights itself.** The extraction prompt (`packages/ontology-manager/src/ontology_manager/prompts.py:339`) *explicitly orders* the LLM: *"PRIORITY: Use domain-specific types (e.g., Gemeente, Ministerie, RegioDeal) over generic types."* The LLM obeys. Then `entity_persistence_service.py::_normalize_entity_type` **deletes** the rich type — it lowercases the label, looks it up in an English-only alias map, finds nothing, and returns `"other"`. The rich type lands in `properties.raw_entity_type` but **nowhere typed**: `primary_type` is null, `type_tags` is empty. **L preserves what the LLM already produces.**

### 1.2 The design — language-agnostic by construction (bake this in)

> **The core bridge is LANGUAGE-AGNOSTIC.** Typing flows through the ontology's *declared* `parent_type` chain, NOT a free-form label guess. Adding a language = adding an ontology (with `parent_type` chains rooting at schema.org bases) — **no per-language code.** Only the L.2 residual alias map is language-specific (curated EN+NL, the user's 98%-coverage constraint).

- **Core (L.1) — agnostic**: extracted label (`Gemeente`) → find its `EntityTypeDefinition` in the applied schema(s) → walk `parent_type` (`Gemeente`→`AdministrativeArea`) to a schema.org base → a **small FIXED `_CANONICAL_BY_SCHEMA_ORG` map (~20 entries)** keyed on stable schema.org English identifiers (`AdministrativeArea→administrative_area`, `GovernmentOrganization→government_organization`, `Deal/GovernmentService→programme`, `Concept→topic`, `CreativeWork→creative_work`, `Legislation→legislation`, `Person→person`, `Organization→organization`, `Place→location`, `Event→event`, `Dataset→dataset`, `Grant→grant`…). Schema.org IDs are stable English identifiers, **maintained ONCE, not per-language.** The original ontology type (`Gemeente`) is stamped into `primary_type` + `type_tags`; `entity_type` becomes the coarse canonical projection.
- **Residual (L.2) — curated EN+NL only**: when the LLM free-forms a label NOT in any applied ontology (`Persoon`, `Organisatie`, `Technologie`, `ABBREVIATION`), a curated **EN+NL alias map** handles it. Truly-unknown → keep the raw label in `primary_type` and coarse to a sensible default (NOT silently `other`). **This is the only language-specific surface.** No LLM/embedding fallback for the residual 2% (explicit user constraint).

### 1.3 Dependencies on / conflicts with other tracks (and the central risk)

- **Depends on**: Track **B.8** (persistence/upsert layer — merged) and the **migration-44 `type_tags`/`primary_type` fields** (B.1a — already in the model + DB, empty). No other track is a hard prerequisite for L.1-L.4.
- **Feeds Track K**: better typing makes the K resolution layer materially better — the K.7a `(canonical_name, entity_type)` relation-endpoint guard and the K.7b aggressive-normalization-behind-type-safety only work when `entity_type` is *correct*. The K.7b finding (`VRO`/`minister van VRO` both `other`) is exactly what L fixes. **L coordinates with the K over-merge corpus** (`tests/fixtures/entity_resolution/must_not_merge.jsonl`) — re-typing must not create new cross-type collisions that defeat K's guard.
- **🔴 CENTRAL RISK — L.5 re-typing CHANGES `entity_type`, which changes the B.8 `hash_id`.** `hash_id = md5(f"{canonical_name}|{entity_type}")` and the upsert dedup key is `(canonical_name, entity_type)`. A row re-typed from `other`→`administrative_area` gets a **new** `hash_id` and a **new** dedup identity. Two consequences: (a) the row must be **re-keyed** (its id/hash recomputed); (b) two rows that were distinct under `other` (e.g. `Groningen/other` the concept and `Groningen/other` the place — both `other`) may **collide** when one becomes `administrative_area` and the other stays `topic`, OR converge if both become the same canonical. **Mitigation (L.5)**: re-type via a **controlled migration** that recomputes `hash_id`, detects resulting collisions, and **merges them through the K.3 `recanonicalization_service` merge semantics** (status=`merged`, `merged_into`, relation re-point, union provenance) rather than overwriting blindly. Dry-run-default, idempotent, reversible. **Decision point L-D4.**
- **Conflict — `_normalize_entity_type` is shared with K.7a**: the relation-endpoint type map (`type_by_name`) at `entity_persistence_service.py:200` calls `_normalize_entity_type`. L.1 changes what that returns (richer canonical). **Regression guard**: K.7a's `test_relation_endpoints_do_not_cross_types` stays green; the type-by-name map gets *more* precise (a win for K.7a), never less.
- **Conflict — Track K migrations**: K took 54-57. **L starts at 58.** No file overlap (K = resolution services, L = persistence typing + ontology bridge).
- **No conflict** with Tracks A/C/D/E/F/G/H/I/J (different files).

### Phase L.5 — Retroactive re-typing of existing entities (the destructive phase)

**Goal**: re-type the **already-persisted** `other`/generic entities WITHOUT re-extraction — every `other` row carries `properties.raw_entity_type` (its original ontology label), so re-running the L.1 bridge + L.2 alias map over it assigns the correct `entity_type` + `primary_type`/`type_tags`. Mirror the **K.3 `recanonicalization_service` pattern**: dry-run-default, idempotent, reversible. **The central risk**: changing `entity_type` changes the B.8 `hash_id` → re-key + collision-merge (see §1.3, L-D4).

**Files to create**:
- `apps/app-main/src/app_main/services/entity_typing/__init__.py`
- `apps/app-main/src/app_main/services/entity_typing/retyping_service.py`:
  - `async plan_retyping(notebook_id: str | None = None) -> RetypePlan` — loads active entities whose `entity_type in {"other", "concept", "topic"}` (the flattened buckets) **and** that carry a `raw_entity_type` (or whose label maps under the new logic); recomputes `new_type = resolve(raw_entity_type, applied_schemas)`; returns a `RetypePlan` of `RetypeAction(entity_id, old_type, new_type, new_primary_type, new_hash_id, collision_target | None)`. **Computes the new `hash_id`** and flags whether re-keying collides with an existing `(canonical_name, new_type)` row. **Dry-run only — no writes.**
  - `async apply_retyping(action: RetypeAction) -> RetypeResult` — within one logical operation: (1) if `collision_target` is set, **route through the K.3 merge** (`recanonicalization_service.apply_merge`) so the re-typed row merges into the existing same-key row with full provenance-union + relation re-point + `status='merged'`; (2) else update `entity_type`/`primary_type`/`type_tags` AND **recompute/re-key `hash_id`** in the same operation. Idempotent: a row already at `new_type` is a no-op.
  - `async apply_plan(plan, *, dry_run=True)` — hard `dry_run` default.
- `apps/app-main/src/app_main/api/routers/entity_typing.py` — `POST /api/entity-typing/plan` (dry-run `RetypePlan`), `POST /api/entity-typing/apply` (explicit action ids only; never "apply all" implicitly — mirrors K.3).
- `apps/app-main/tests/test_retyping_service.py`, `packages/surrealdb-service/tests/test_retyping_roundtrip.py` (testcontainers).

**Files to modify**:
- `packages/surrealdb-service/src/surrealdb_service/repositories/entity.py` — add `rekey_entity(entity_id, new_type, new_primary_type, new_type_tags, new_hash_id)` that updates type fields AND the hash-derived key atomically; reuse the K.3 `repoint_relations`/`mark_merged` helpers for the collision path.
- `docs/tracks/L-entity-typing/` — record the re-type run's before/after counts.

**Acceptance criteria** (falsifiable):
1. `plan_retyping()` over a seeded set with an `other` row carrying `raw_entity_type="Gemeente"` returns a `RetypeAction` with `new_type="administrative_area"`, `new_primary_type="Gemeente"`, and the **recomputed `hash_id`**. **No writes occurred** (re-fetch shows it still `other`).
2. The plan flags a **collision**: a row `(canonical_name="Groningen", other)` re-typing to `administrative_area` where a `(Groningen, administrative_area)` row already exists → `collision_target` is set (not a blind overwrite).
3. `apply_retyping` on a non-colliding action: the row's `entity_type`/`primary_type`/`type_tags` and `hash_id` are updated; a subsequent normal upsert of `(Groningen, administrative_area)` finds the re-keyed row (the dedup key now matches).
4. `apply_retyping` on a colliding action: routes through the K.3 merge — the re-typed row becomes `status='merged'`, `merged_into` the existing row, relations re-pointed, provenance unioned. **No data lost, reversible** via `merged_into`.
5. Re-running `apply_retyping` on the same action is a no-op (idempotent).
6. `apply_plan(plan)` with the default (`dry_run=True`) performs **zero** writes (write-count spy == 0).
7. **B.8 contract preserved post-rekey**: every re-typed row's `hash_id == md5(f"{canonical_name}|{new_type}")` (the derive-rule is honoured with the new type); a fresh ingest dedups against the re-keyed row correctly.
8. **K coordination**: re-typing does NOT create a cross-type collision that defeats the K `(name,type)` guard — over the K `must_not_merge` corpus, no two genuinely-distinct entities end up sharing `(canonical_name, entity_type)` after re-typing (assert false-merge count == 0).

**Tests required**:
- Unit (`test_retyping_service.py`): re-type from `raw_entity_type`, collision detection, dry-run-no-writes, idempotency, hash_id recompute.
- Integration (`test_retyping_roundtrip.py`, `@requires_docker`): seed flattened entities + relations → plan → apply (collision + non-collision) → assert re-key, merge-on-collision, relation integrity, idempotency, B.8 dedup-after.

**PR boundary**: ONE PR titled `feat(typing): retroactive re-typing of existing entities — dry-run + reviewable + hash_id re-key/merge (L.5)`.

**Effort estimate**: **2.5–3 days**. Reviewer cycle budget: ×2.0 (mutates the live KG + changes `hash_id` — the highest-risk phase; dry-run/idempotency/collision-merge are the safety net).

**Risks**: 🔴 (a) **the central risk — `hash_id` change on re-typing** (§1.3): a bad re-key orphans relations or collides silently — mitigated by collision-detection-before-apply, routing collisions through the proven K.3 merge (soft `status='merged'`, reversible), recomputing `hash_id` deterministically, and the dry-run default. (b) re-typing a row whose `raw_entity_type` is itself noise (`ABBREVIATION`) — the L.2 fallback applies (preserve label, don't force `other`); such rows can be excluded from the auto-plan and listed for review. (c) non-atomic SELECT-then-UPDATE (inherited from `upsert_entity`) — run as an offline/maintenance op, no concurrent writers, documented precondition (same as K.3). ## 4. Per-schema notes (the "what could be improved in the different schemas" answer)

> **The ontologies are high-quality, correctly Dutch + layered, and the LLM uses them correctly.** The per-schema refinement is NOT a rewrite — it is three small things, all in service of the L.1 bridge:

- **(a) Ensure every `entity_type`'s `parent_type` chain reaches a schema.org base that maps to a canonical** (the L.6 orphan audit). Verified gaps from reading the YAMLs:
  - `government`: `Gemeente`/`Provincie`→`AdministrativeArea` ✅; `Ministerie`/`Uitvoeringsorganisatie`→`GovernmentOrganization` ✅; `FunctioneleRegio`/`Wijk`/`Grensregio`/`Land`/`BuitenlandseRegio`→`Place` ✅. **But `AdministrativeArea` and `GovernmentOrganization` are defined in `policy.yaml`, not `schema_core.yaml`** — confirm the bridge resolves these whether or not `policy` is loaded (map them in `_CANONICAL_BY_SCHEMA_ORG` directly so the chain terminates at the *name*, not a loaded definition).
  - `deals`: `Deal`→`GovernmentService`, `RegioDeal`/`Woondeal`/`CityDeal`→`Deal`, `Akkoord`→`GovernmentService`, `Project`→`CreativeWork`. **`GovernmentService` is not a schema_core base** — map `GovernmentService`→`programme` (L.3) directly in the bridge map (terminate at the name).
  - `policy_themes`: `BeleidsThema`/`BeleidsPijler`/`Indicator`→`Concept`. **`Concept` is not a schema_core top-level** (schema_core has `DefinedTerm`) — map `Concept→topic` in the bridge **or** add `canonical: topic` on these types (L.6).

## 5. Decision points (escalate to user)

- **L-D1 — extend-enum vs ontology-type-as-`entity_type`** (L.3): *Recommendation*: **extend-enum** — `entity_type` stays a small coarse projection (add `programme`/`technology`), `primary_type`/`type_tags` hold the rich ontology type (the L.1 split). - **🔴 L-D4 — L.5 `hash_id` change mechanism** (the central risk): re-key-in-place via the service dry-run/apply (reusing K.3 merge for collisions) vs a blind one-shot migration. *Recommendation*: **service-driven, dry-run-default, collision-merge through K.3** — reviewable and reversible.
