### 1.3 The over-merge invariant (the central risk — applies to every phase that changes matching)

> **Over-merging (false merges that conflate distinct real entities) is worse than under-merging (fragmentation).** A fragmented `BZK` is annoying; a `BZK`-merged-into-`Financiën` is *wrong data* the user cannot easily detect. Every phase that changes the matching/normalization behaviour (K.1, K.2, K.4, K.5) ships with a **precision guard** and is tested against a **must-NOT-merge corpus** alongside the must-merge corpus.

- **Precision strategy**: matching changes are **tail-preserving and conservative-by-default**.
  - K.1 strips *prefixes* (articles, role/org leaders) but **the discriminating tail must survive**: `Minister van BZK` and `Minister van Financiën` must stay distinct because their tails differ; only `Ministerie van BZK` ↔ `BZK` (same tail/referent) merge. The strip rule never collapses two names whose normalized tails differ.
  - K.2 abbreviation expansion is a **curated, closed allow-list** (no fuzzy abbreviation guessing); an unknown abbreviation is left untouched rather than guessed.
  - K.4 vocabulary linking only merges when an entity maps to a **single** `reference_entity` with confidence above a threshold; ambiguous (multi-candidate) links are recorded as *candidates*, not auto-merged.
  - K.5 fuzzy/embedding merges above the auto-threshold are applied; the band between review-threshold and auto-threshold is **queued for human review** (K.6), never silently merged.
- **The must-NOT-merge corpus** (`tests/fixtures/entity_resolution/must_not_merge.jsonl`) is built in K.1 and **extended in every subsequent matching phase**. Each phase's acceptance criteria include "false-merge count over the must-NOT-merge corpus == 0".
- **The measurement metric** (K.1, re-run each phase): over the live Convenant entity set, report **fragmentation-reduction** (distinct-canonical-count before→after, and merged-cluster sizes) **and false-merge count** (pairs from the must-NOT-merge corpus that ended in the same cluster). A phase is acceptable only if fragmentation drops **and** false-merges stay 0.

### Phase K.3 — Retroactive canonicalization/merge over already-persisted entities

**Goal**: dedup the KG **that already exists** (the fragmented 897). A **dry-run** that re-normalizes every persisted entity under the K.1+K.2 normalizer, groups entities whose new canonical form collides, and lists the proposed merges; a **reviewable apply** that re-points relations, merges `aliases`/`source_documents`/`confidence` per the B.8 upsert merge semantics, marks losers `status='merged'` + `merged_into`, and records the surface forms as `entity_alias` rows. This is the operation that collapses 897 → fewer.

**Files to create**:
- `apps/app-main/src/app_main/services/entity_resolution/__init__.py`
- `apps/app-main/src/app_main/services/entity_resolution/recanonicalization_service.py`:
  - `async plan_merges(notebook_id: str | None = None) -> MergePlan` — loads active entities, computes `new_canonical = normalize_entity_name(canonical_name)` per entity, groups by `(new_canonical, entity_type)`, returns a `MergePlan` of `MergeCluster(canonical_winner, losers, member_surface_forms, total_source_docs)`. Winner-selection rule: highest `confidence`, tie-break most `source_documents`, then oldest `created_at` (stable). **Dry-run only — no writes.**
  - `async apply_merge(cluster: MergeCluster) -> MergeResult` — within one logical operation: (1) UPDATE all `relation` edges pointing at a loser to point at the winner (dedup resulting parallel edges); (2) merge `source_documents`/`type_tags`/`provenance_chain` (union) + `confidence` (max) + `properties` (overlay) into the winner — **identical semantics to `upsert_entity`**, reused not reimplemented; (3) CREATE `entity_alias` rows for each loser's surface form → winner; (4) set each loser `status='merged'`, `merged_into=<winner id>`. Idempotent: re-applying a cluster whose losers are already `merged` is a no-op.
  - `async apply_plan(plan, *, dry_run=True) -> ...` — batch wrapper with a hard `dry_run` default.
- `migrations/54.surrealql` + `54_down.surrealql` — `DEFINE FIELD IF NOT EXISTS aliases ON entity FLEXIBLE TYPE array DEFAULT [];` (first-class per-entity alias list complementing the `entity_alias` edges; needed by K.4/K.6). (External_ids field lands in K.4's migration.) Plus an index to query `status='merged'`/`merged_into` efficiently if not already present.
- `apps/app-main/src/app_main/api/routers/entity_resolution.py` — `POST /api/entity-resolution/plan` (returns the dry-run `MergePlan`), `POST /api/entity-resolution/apply` (applies a reviewed plan/cluster list; requires explicit cluster ids, never "apply all" implicitly).

### Phase K.5 — Fuzzy/embedding candidate dedup + merge step + user-overlay

**Goal**: wire the entity-filtering pipeline's existing fuzzy/embedding dedup (`FuzzyDedupConfig`/`EmbeddingDedupConfig`/`KGResolutionConfig`) into a **measured + tuned** candidate-merge step that proposes merges the deterministic normalizer (K.1/K.2) cannot catch (typo variants, near-duplicate phrasings), feeding the K.3 reviewable-merge machinery. Add the **user-overlay**: global + per-notebook alias overrides that force-merge or force-split specific pairs (the human escape hatch over the automated matcher).

**Files to create**:
- `migrations/56.surrealql` + `56_down.surrealql` — `DEFINE TABLE alias_overlay SCHEMAFULL;` fields: `scope` (`global` | `notebook`), `notebook` (`option<record<notebook>>`), `kind` (`merge` | `split`), `name_a`, `name_b`, `entity_type`, `created_at`. (force-merge = treat as same; force-split = never merge even if the matcher says so — the split rule is the ultimate over-merge backstop.)
- `apps/app-main/src/app_main/services/entity_resolution/candidate_dedup_service.py` — `async propose_candidates(notebook_id=None) -> list[MergeCandidate]` running the entity-filtering fuzzy + embedding resolvers over persisted entities; partitions results into **auto-merge** (≥ auto-threshold), **review** (review-threshold..auto-threshold → queued, never silent), and **reject** (< review-threshold). Applies the `alias_overlay` force-split rule as a hard veto and force-merge as a hard include.
- `apps/app-main/src/app_main/services/entity_resolution/overlay_service.py` — CRUD for `alias_overlay` (global + per-notebook), consulted by `candidate_dedup_service` and by `name_normalizer`'s override loader (K.2 seam).
- `packages/surrealdb-service/src/surrealdb_service/repositories/alias_overlay.py`.
- Tests: `apps/app-main/tests/test_candidate_dedup_service.py`, `test_overlay_service.py`, `packages/surrealdb-service/tests/test_alias_overlay_roundtrip.py`.

**Files to modify**:
- `pipelines/entity-filtering/src/entity_filtering/config.py` — tune the default thresholds based on the K.5 measurement (record the chosen `FuzzyDedupConfig.similarity_threshold` / `EmbeddingDedupConfig.similarity_threshold` with the fragmentation-vs-false-merge evidence). Additive: add an explicit `auto_merge_threshold` / `review_threshold` split if not already expressible.
- `apps/app-main/src/app_main/api/routers/entity_resolution.py` — add `GET /api/entity-resolution/candidates` (review queue) + overlay endpoints (`POST/DELETE /api/entity-resolution/overlay`).

**Acceptance criteria** (falsifiable):
1. `propose_candidates()` over a set with a typo pair (`"Koninkrijksrelaties"` vs an OCR-mangled `"Koninkrijksreiaties"`) proposes them as an auto-merge or review candidate (caught by fuzzy, not by the deterministic normalizer).

5. A `force-merge` overlay (scope `notebook`) causes `A`↔`B` to be proposed/applied **only** within that notebook; a different notebook is unaffected (per-notebook isolation).
6. The chosen thresholds are recorded with a measurement: at the tuned values, fragmentation drops further vs K.2 while false-merges stay 0.

## 4. Decision points (escalate to user before / during implementation)

- **K-D1 — first-class `entity.aliases`/`external_ids` fields vs `entity_alias` table only**: *Recommendation*: do **both** — keep the `entity_alias` table (migration 39, carries per-alias provenance/confidence/source_document) as the source of truth, and add denormalized `aliases[]`/`external_ids[]` array fields on `entity` (K.3/K.4 migrations) for cheap read/display and exporter use. The arrays are derived; the table is authoritative. *Trade-off*: mild write-time denormalization vs a join on every read. **Recommended: both.** Confirm.
- **K-D2 — TOOI source + refresh mechanism**: the exact TOOI access (SPARQL endpoint vs bulk RDF/JSON download) and the "monthly refresh" trigger (cron vs manual `POST /api/vocabulary/refresh` vs app-startup-if-stale) are **not resolvable from the codebase** — the implementer must confirm the TOOI distribution format and the desired refresh cadence before K.4. *Recommendation*: bulk-download into `reference_entity` + a manual+scheduled `refresh()` that stamps `last_validated`; gate on Q9's "monthly refresh" intent. **This is the one item the implementer cannot self-resolve.**
- **K-D3 — auto-merge vs review-only for K.3/K.5**: *Recommendation*: K.3 deterministic-collision merges and K.5 ≥auto-threshold merges may auto-apply **only** behind an explicit operator action (the dry-run/review default); the uncertain band is always human-reviewed (K.6). Confirm that a fully-automatic (no-review) bulk apply is **not** wanted for V1 (the over-merge risk argues against it).
- **K-D4 — where the user-overlay precedence sits**: per-notebook overlay beats global; both beat the automated matcher (force-split is an absolute veto). Confirm this precedence.
- **K-D5 — does retroactive merge (K.3) run per-notebook or global**: *Recommendation*: support both (the `notebook_id=None` global plan + a scoped plan); default the UI to per-notebook to limit blast radius. Confirm.
