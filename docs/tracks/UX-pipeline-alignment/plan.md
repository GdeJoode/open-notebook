## Decisions (locked 2026-07-01)
1. **`processing_stage` is the spine.** One canonical `PipelineStatus` component (3 variants: `live` / `card` / `detail`) reads `processing_stage` from GET `/sources/{id}` and renders the 5 stages in runtime order (Ingest → Embed → Extract → Graph → Complete) with Insights as a parallel sub-track. Output counts are enrichment on `done` nodes, never the status source.
2. **Job status is a second axis, not the spine.** GET `/sources/{id}/status` (`new|queued|running|completed|failed|paused_for_review`) only drives the `active`/spinner state of the *current* node; it never determines which stage a source is in.
3. **Lean creation flow:** replace the 9-step wizard with ~4 steps (Input → Organize → live `PipelineStatus` tracker → Done), correct order (Embed before Extract), streaming log console kept under the live tracker.
4. **Config relocation:** the mandatory "Config" step leaves the creation flow. Parser/Docling config's home = the existing post-ingest **Reprocess** dialog (output-driven, reversible). A collapsed "Advanced ingestion settings" disclosure on the Input screen covers power-user overrides, defaulted to Auto.
5. **Manual controls become recovery actions:** the leftover "Run X" buttons are reframed as re-run/recovery, meaningful only on `failed` / `awaiting_schema_review` stages. The stale "run POST …/regenerate manually" guidance is removed (GRAPH is automatic now).
6. **Contradictions** surface only if verdicts exist — on-demand, low priority, shipped as a deferred stub in UX.6.
7. **Additive & independently shippable.** Backend types/hooks first, then the shared component, then wire each surface, then the flow refactor, then cleanup. Each phase is one PR on a feature branch.

## Phase UX.2 — Canonical `PipelineStatus` component + stage state machine (Shared component)
**Goal**: one component that renders the 5-stage spine (+ Insights sub-track) from `processing_stage`, in 3 variants, with a pure, unit-tested mapping module. This is the reusable core UX.3–UX.5 wire in.

**Files to create**
- `frontend/src/lib/pipeline/pipeline-stages.ts` — pure module (no React). Exports the ordered stage model `[Ingest, Embed, Extract, Graph, Complete]` + the `Insights` parallel node, and `derivePipelineNodes({ processingStage, jobStatus, counts })` → `PipelineNode[]` where each node has `{ key, label, state, count?, deepLinkTab?, action? }` and `state ∈ 'pending' | 'active' | 'done' | 'gated' | 'failed'`. Rules: stage index from `processing_stage` marks earlier stages `done` and the current as `active` **only when** `jobStatus ∈ {running,queued,new}`, else `done`; `awaiting_schema_review` ⇒ Extract node `gated`; `failed` ⇒ current node `failed`; counts (`embedded_chunks`, `entity_count`, `insights_count`, graph-present flag) hydrate `done` nodes as enrichment. This is the successor to `derivePipelineStatuses`.
- `frontend/src/components/sources/pipeline/PipelineStatus.tsx` — presentational component `variant: 'live' | 'card' | 'detail'` consuming `derivePipelineNodes`. `live` = full horizontal tracker with spinners + streaming-log slot; `card` = 5-segment mini bar + current-stage label; `detail` = collapsible spine row. Per-node: `pending` (muted), `active` (spinner), `done` (check + count e.g. "24 chunks" / "18 entities"), `gated` (amber + "Review schema" action), `failed` (red + "Retry" action). Node click fires an `onNodeClick(deepLinkTab)` callback (deep-link wiring done by the consuming surface).

**Files to modify**
- `frontend/src/components/sources/pipeline/index.ts` (or the barrel that exports pipeline components, create if absent) — export `PipelineStatus`.

**Acceptance criteria**
1. `derivePipelineNodes` returns nodes in runtime order `Ingest → Embed → Extract → Graph → Complete` (Embed **before** Extract) with `Insights` flagged as a parallel sub-track (not inline in the 5-stage spine).
2. State mapping is exhaustive and asserted for every `ProcessingStage`: `ingested`→Ingest done/active; `embedded`→Embed done; `extracted`→Extract done; `awaiting_schema_review`→Extract `gated`; `graphed`→Graph done; `complete`→all done incl. Complete; `failed`→current node `failed`.
3. `active` vs `done` for the current node is driven by `jobStatus` (running/queued ⇒ `active` spinner; completed/absent ⇒ `done`) — asserted by a test that flips only `jobStatus`.
4. Counts appear only on `done` nodes and never change a node's `state` (a node with `entity_count=0` but stage `graphed` still renders Extract `done`).
5. All three variants render each of the 5 node states without crashing (default/active/gated/failed/empty), and are keyboard-accessible: each node is a focusable control with an `aria-label` describing stage + state; the gated/failed actions are reachable by Tab and expose `aria-label`.
6. Rendering with `processing_stage === undefined` yields an all-`pending` spine (no crash) — the graceful pre-migration/list fallback.

**Tests required**
- Unit: `frontend/src/lib/pipeline/pipeline-stages.test.ts` — full stage×jobStatus×counts matrix (the successor to today's `derivePipelineStatuses` logic).
- Component unit: `frontend/src/components/sources/pipeline/__tests__/PipelineStatus.test.tsx` — renders all 5 states per variant, asserts count enrichment on `done` nodes, gated/failed actions present + labelled, node-click callback fires with the expected `deepLinkTab`.
- Mandatory (from `frontend/`): `npm run lint` · `vitest run src/lib/pipeline src/components/sources/pipeline`.

**PR boundary**: ONE PR — `feat(ux2): canonical PipelineStatus component + stage state machine`.
**Branch**: `track/ux2-pipeline-status-component`. **Depends on**: UX.1.
**Effort estimate**: 2–3 days.

## Risk assessment
1. **`processing_stage` not on the list endpoint** → SourceCard can't read the spine from list data. Mitigation: per-card `useSourcePipeline` fetch gated to non-terminal cards (UX.3), with an all-`pending` fallback; flagged as an Open Question because a one-line backend addition to `SourceListResponse` is cleaner than N per-card GETs on large notebooks.
2. **Polling axis switch** → moving the stage source from `/sources/{id}/status` to `/sources/{id}` changes request patterns. Mitigation: `useSourcePipeline` stops at terminal/gated stages (UX.1); `useSourceStatus` retained for the `active`-node spinner only; assert no runaway polling in UX.1/UX.3 tests.
3. **Wizard refactor blast radius** (UX.5) — `CreateSourcePipeline.tsx` is large and drives multi-file batching. Mitigation: UX.5 comes after the component + hooks are proven (UX.1/UX.2), keeps batching behavior, and lands with both unit and E2E coverage.
4. **Orphaned tab components** — deleting `…/tabs/*` risks breaking a non-obvious importer. Mitigation: grep for importers before deletion (UX.6 AC4); leave files if any importer remains.
5. **Contradictions endpoint may not exist** — surfacing verdicts could couple to an absent API. Mitigation: ship as a deferred, data-absent-safe stub (UX.6); no hard backend dependency.
6. **Stage/job-status skew** — a source can be `graphed` while a late job is still `running`, or `complete` with counts still catching up. Mitigation: the state machine treats `processing_stage` as authoritative for node completion and `jobStatus` only for the current node's spinner (UX.2 AC3); counts are enrichment only (AC4).
