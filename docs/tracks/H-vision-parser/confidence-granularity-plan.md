## 1. Context

- **Reference**: `docs/tracks/A-mineru/CONFIDENCE_GRANULARITY_NOTE.md` (Optie A);
  `docs/FEATURE_ROADMAP.md` Track H (H1 "region-of-interest hints").
- **Track goal**: Move docling↔MinerU auto-fallback from **per-document
  all-or-nothing** to **per-segment (per-page)** confidence, so docling keeps
  the clean pages and MinerU re-parses only the low-confidence pages, producing
  a **hybrid** IngestionResult. Delivers a standalone quality win for the
  existing auto-fallback and is the gating prerequisite for Track H's
  element-level vision routing.
- **This is a prerequisite sub-track**, not a full feature track — there is no
  UI phase in scope (the badge-copy change is a small data/label update inside
  the existing A.1c badge, planned in §H0.4, not a new component).

### Why "per-page", not "per-chunk" or "per-element" (design decision D1)

The note frames the unit as "per-chunk (of per pagina)". The codebase makes
**per-page** the correct routing/merge unit:

- `ExtractedDocument.pages` (`pipelines/ingestion/src/ingestion/models/document.py`)
  is already page-organized (`PageContent.page_number`, `.elements/.tables/.images`).
  Scoring a `PageContent` is a near-mechanical refactor of the existing
  element-iteration in `confidence.py`.
- **MinerU's own boundary is the page**: `<stem>_content_list.json` items are
  keyed by `page_idx` (see `services/mineru/api.py::_summarise_content_list`).
  A MinerU re-parse can only be sliced/merged along page boundaries, not chunk
  boundaries (chunks are a *downstream* artefact of `ChunkExtractor`, produced
  after parsing).
- **Merge is clean at the page boundary**: splice `docling.pages[i]` vs
  `mineru.pages[i]` with no cross-page element reconciliation.
- **Per-chunk is derivable, not primary**: `chunk.physical_page` (migration 10)
  maps every chunk to a page, so the "3/12 chunks" badge the note wants is
  computed by counting chunks whose `physical_page` fell in a re-parsed page
  range. Per-chunk confidence is *propagated from* per-page (§H0.3), not scored
  independently.
- **Per-element is rejected**: signals like `text_density` and `heading_rate`
  need a page-sized denominator; per-element has no meaningful density signal
  and no MinerU re-parse boundary.

- **Dependencies (must-be-done-first)**: none. All plumbing (A.1c auto-fallback,
  confidence scoring, FLEXIBLE metadata bags, MinerU HTTP client) is already on
  `main`.
- **Blocks**: Track H (H2 element/region vision routing explicitly needs Optie A
  per the note's §"Relatie met Track H").
- **Conflicts (files touched concurrently)**: `confidence.py`, `auto_fallback.py`,
  `source_extractor.py` are core A-track files. No other in-flight track is known
  to touch parsing; if Track H work starts before this lands, it must rebase on
  these phases.

### Phase H0.1 — Per-page confidence scoring (Backend)

**Goal**: `confidence.py` emits a score **per page** plus a derived document-level
aggregate, without breaking the existing doc-level callers.

**Files to modify**:
- `apps/app-main/src/app_main/services/parsing/confidence.py` — add
  `PageConfidence` dataclass (`page_number: int`, `overall: float`,
  `signals: Dict[str, float]`, `decision: Literal["accept","fallback"]`); add
  `score_docling_pages(result, *, threshold) -> list[PageConfidence]` that runs
  the existing 6 signals scoped to one `PageContent`; refactor the existing
  helpers (`_ocr_confidence`, `_text_density`, `_heading_rate`, `_table_success`,
  `_image_text_ratio`, `_unknown_element_ratio`) to accept a per-page element
  slice; keep `score_docling_extraction` as-is on the surface but re-implement its
  `overall`/`signals` as a **page-count-weighted aggregate** of the per-page
  scores (identical result for single-page docs; near-identical for multi-page).
  Add `pages: list[PageConfidence] = field(default_factory=list)` to
  `DoclingConfidenceScore` (additive, defaulted → back-compat).

**Files to create**: none.

**Acceptance criteria** (numbered, testable):
1. `score_docling_pages(result)` returns one `PageConfidence` per
   `document.pages` entry, each with all 6 signals populated.
2. For a single-page fake document, `score_docling_extraction(result).overall`
   equals `score_docling_pages(result)[0].overall` within 1e-9.
3. For a mixed fake document (N clean pages + M scanned pages), the clean pages
   score ≥ threshold and the scanned pages score < threshold (per-page decision
   is correct).
4. `document is None` (audio) path still returns the neutral 1.0 doc-level score
   AND an empty `.pages` list (no crash).
5. `SIGNAL_WEIGHTS` still sums to 1.0 (existing assertion unchanged).
6. Existing `score_docling_extraction` public signature and return type are
   unchanged; all current callers compile without edits.

**Tests required**:
- Unit: extend `apps/app-main/tests/test_docling_confidence.py` — per-page split,
  single-page equivalence (AC2), mixed-doc per-page decisions (AC3), audio neutral
  (AC4), aggregate-equals-weighted-mean property.
- No docker required (pure function, lightweight fakes — the existing test style).

**PR boundary**: `refactor(confidence): per-page docling scoring + derived doc aggregate`

**Effort estimate**: 1.5–2 days

### Phase H0.2 — Hybrid per-page merge in auto-fallback (Backend) 🔴 RISKIEST

**Goal**: When some (not all) pages fall below threshold, re-parse via MinerU and
**merge** docling's clean pages with MinerU's re-parsed pages into one
`IngestionResult`. This is the hard part and the phase most likely to slip.

**Interim vs full architecture decision (D2)** — the same interim-guard pattern as
M.4:
- **Interim (this phase, no MinerU change)**: run MinerU over the **whole
  document** (the only thing the current `MineruHttpClient.process(path)` +
  `services/mineru/api.py` support), then **splice**: keep docling `PageContent`
  for accept-pages, substitute MinerU `PageContent` for fallback-pages, rebuild a
  single `ExtractedDocument` (re-derive `full_text`, `full_markdown`, `all_tables`,
  `all_images`, `page_count`). **Delivers the hybrid QUALITY win + all metadata;
  does NOT deliver the perf win** (MinerU still runs the whole doc). Honest about
  this — the perf win is H0.5.
- **Full (deferred to H0.5)**: page-range MinerU re-parse for a real perf win —
  requires new MinerU service + client capability (see H0.5).

**Files to create**:
- `apps/app-main/src/app_main/services/parsing/page_merge.py` — pure
  `merge_pages(docling_result, mineru_result, fallback_page_numbers) ->
  IngestionResult`. Page-indexed splice + document re-aggregation. Pure/testable,
  no I/O.

**Files to modify**:
- `apps/app-main/src/app_main/services/parsing/auto_fallback.py` — new decision
  branch: after `score_docling_pages`, if **all** pages accept → keep docling
  (unchanged); if **all** pages fallback → full MinerU (unchanged, current
  behaviour); if **mixed** → run MinerU (interim: whole doc), call `merge_pages`,
  set `engine_used="hybrid"`. Extend the return `score` object so callers can read
  which pages were re-parsed. Preserve the existing whole-doc all-or-nothing paths
  exactly (docling-failed, both-failed, MinerU-failed-after-fallback → degraded
  docling) so no current test regresses.
- `apps/app-main/src/app_main/services/parsing/__init__.py` — export `merge_pages`.

**Acceptance criteria**:
1. Mixed doc (docling clean pages 1–3, scanned pages 4–5): result contains
   docling `PageContent` for 1–3 and MinerU `PageContent` for 4–5; `page_count`,
   `full_text`, `all_tables`, `all_images` are consistently re-aggregated.
2. `engine_used == "hybrid"` iff at least one page was kept AND at least one page
   was re-parsed; `"docling"` when all kept; `"mineru"` when all re-parsed.
3. Page ordering preserved (merged `pages` sorted by `page_number`, 1-indexed, no
   gaps/dupes).
4. MinerU-run-failed on a mixed doc → falls back to full docling result with a
   WARNING (never strands the user); `engine_used == "docling"`,
   fallback-triggered still true (parity with existing degraded path).
5. `merge_pages` is pure (no I/O) and idempotent; merging with an empty
   fallback-set returns the docling result unchanged.
6. All existing `test_auto_fallback.py` scenarios still pass unchanged
   (all-accept, all-fallback, docling-raised, both-failed).

**Tests required**:
- Unit: new `apps/app-main/tests/test_page_merge.py` — splice correctness (AC1/3),
  empty-set no-op (AC5), aggregation re-derivation.
- Unit: extend `apps/app-main/tests/test_auto_fallback.py` — mixed-doc hybrid path
  (AC1/2), MinerU-fail-on-mixed degraded path (AC4), regression of the four
  existing all-or-nothing paths (AC6). Mock both clients (existing style).
- `requires_docker`: **not required** for this phase (merge is pure; clients are
  mocked). A real MinerU splice is validated in H0.5 / integration smoke.

**PR boundary**: `feat(auto-fallback): hybrid per-page docling+MinerU merge (interim full-run)`

**Effort estimate**: 2.5–3 days (riskiest — see §3)

### Phase H0.5 — MinerU page-range re-parse (Backend) — GATED FOLLOW-UP

**Goal**: Replace the H0.2 interim whole-doc MinerU run with a **page-range
re-parse** so a 500-page PDF with 20 bad pages no longer pays for a full MinerU
run. This is where the **performance** win in the note lands.

**Gate (must verify BEFORE building)**: our MinerU wrapper does **not** currently
expose page range — `services/mineru/api.py` shells
`mineru -p <in> -o <out> -b <backend>` with no `-s/-e`. This phase is only viable
if the installed MinerU CLI supports page-range flags (`-s/--start`, `-e/--end` in
MinerU 2.x). **Verify against the pinned MinerU version first** (WebFetch official
MinerU CLI docs + `mineru --help` in the service container). If page-range is
unsupported, H0.5 is **not feasible** and the interim (H0.2) is the permanent
answer for the quality win — record that outcome and stop.

**Files to modify** (only if the gate passes):
- `services/mineru/api.py` — add optional `start_page:int|None`,
  `end_page:int|None` to `ProcessRequest`; when set, append `-s/-e` to the CLI
  cmd. Output paths unchanged (page_idx in `content_list.json` remains
  page-absolute — verify re-index offset).
- `apps/app-main/src/app_main/services/mineru_http_client.py` — `process` gains
  optional `page_range: tuple[int,int]|None`; threaded into the `/process`
  payload.
- `apps/app-main/src/app_main/services/parsing/auto_fallback.py` — mixed-doc
  branch computes the minimal contiguous fallback page-range(s) and calls MinerU
  per range instead of whole-doc; `merge_pages` reused unchanged. Handle the
  page_idx offset so re-parsed pages splice back at their absolute page numbers.

**Acceptance criteria**:
1. (Gate) A written verification note records whether the pinned MinerU CLI
   supports page-range; phase proceeds only if yes.
2. Mixed doc: MinerU is invoked with a page-range covering only fallback pages;
   returned pages re-index to their absolute page numbers before merge.
3. Merged output is byte-for-byte equivalent (same pages, same order) to the
   H0.2 interim full-run+splice for the same document (correctness parity).
4. Metric records `pages_reparsed` == range size (not `pages_total`).

**Tests required**:
- Unit: page-range computation from a per-page decision list (contiguous-range
  extraction, multi-gap handling).
- `requires_docker` (MinerU service): one integration test that a page-range

**PR boundary**: `feat(mineru): page-range re-parse for hybrid fallback perf win`

**Effort estimate**: 2–3 days (plus the gate verification, ~0.5 day)

## 3. Risk assessment

- **Risk (🔴 highest): Hybrid page-merge correctness (H0.2)** — re-aggregating
  `full_text`/`full_markdown`/`all_tables`/`all_images` from spliced pages can
  drift from what a single-engine run produces (ordering, dedup, page markers),
  breaking downstream chunking + `PdfChunkViewer` overlays.
  *Mitigation*: keep `merge_pages` pure + property-tested; assert bbox/page
  invariants (the shared 0–1 TOPLEFT convention in `document.py`); regression-test
  the four existing all-or-nothing paths unchanged; validate a real spliced doc in
  H0.5 integration before trusting it in prod.
- **Risk: docling vs MinerU page-index misalignment** — docling `page_number`
  (1-indexed) vs MinerU `page_idx` (0-indexed in `content_list.json`). An
  off-by-one silently swaps clean/scanned pages.
  *Mitigation*: normalize both to the 1-indexed `PageContent.page_number` at the
  merge boundary; explicit test with a doc where page N and N+1 differ in quality.
- **Risk: H0.5 gate fails (MinerU CLI has no page-range)** — the perf win becomes
  unbuildable; interim full-run is the ceiling.
  *Mitigation*: gate is verified first; quality win (H0.2) is independent and
  already shipped, so a failed gate costs nothing already built.
- **Risk: per-page scoring changes the aggregate → threshold-tuning regression**
  — the derived weighted aggregate may not exactly equal the old monolithic score,
  shifting which docs fall back.
  *Mitigation*: AC2 (single-page equivalence) + an aggregate-equals-weighted-mean
  property test; if multi-page aggregates drift materially, keep the old
  whole-doc aggregate formula and expose per-page purely additively.
- **Risk: chunk-stamp coupling to `physical_page`** — chunks with missing/zero
  `physical_page` (non-paginated inputs) get no confidence stamp.
  *Mitigation*: guard the stamp on a present `physical_page`; absence is
  acceptable (AC3 semantics — no per-page data ⇒ no stamp).

## 5. Deferred / needs-user-decision (OUT OF SCOPE)

The **vision tier** (Track H proper) is explicitly out of scope and gated on two
user decisions that this plan does NOT resolve:

- **Gate A — YAGNI / real-problem confirmation**: the roadmap requires a live-test
  to confirm that tables/figures (the vision-model's target) are an *actual*
  extraction problem in practice, not a hypothetical. Per the note's own
  recommendation ("Optie C for now… first test whether the simple version
  suffices"), the vision tier should not be built until the live-test justifies
  it. **This per-page prerequisite is worth building regardless** (it improves the
  existing docling↔MinerU fallback), but H1/H2/H3 wait on this signal.
- **Gate B — vision-model choice**: local GPU vs hosted model, weighed against
  **budget** and **data-sovereignty** (cf. the per-source `private` sticky
  override in `source.py` — a hosted vision model would need to honour it). No
  vision service, routing, or model can be planned until this is decided.

Deferred items dependent on the above (NOT planned here):
- **H1** vision parsing service (+ the *bbox/region-of-interest* hints — note that
  MinerU CLI has **no bbox capability**; region hints are a genuinely new,
  vision-specific surface, distinct from the page-range in H0.5).
- **H2** three-way / per-element routing (docling ↔ MinerU ↔ vision). This is what
  consumes the per-page/per-chunk confidence delivered here.
- **H3** UI "5th engine option" + any vision-specific badge states.

Also deferred within *this* sub-track:
- **H0.5** perf optimization is itself gated on the MinerU-CLI page-range
  verification (§H0.5 gate). If that fails, the interim whole-doc run (H0.2) is the
  permanent quality answer and no perf win is available without a MinerU upgrade.

## 7. What reuses existing plumbing vs. what is genuinely new

**Reuses (low risk)**:
- Per-page scoring — mechanical refactor of the existing 6-signal helpers scoped
  to `PageContent` (H0.1).
- Persistence — rides the existing FLEXIBLE `source.metadata` + `chunk.metadata`
  bags; **no migration** (H0.3).
- Metrics — extends the existing single `extraction.auto_fallback` FLEXIBLE
  payload; no cardinality/schema change (H0.4).
- Badge — existing A.1c badge component reads `source.metadata`; we only enrich
  the data (H0.4).

**Genuinely new (higher risk)**:
- Hybrid page-splice + document re-aggregation (`page_merge.py`) — new logic, the
  riskiest phase (H0.2).
- MinerU **page-range** capability — new service `ProcessRequest` params + client
  threading; **not supported today**, gated on CLI verification (H0.5).
- MinerU **bbox/region** hints — NOT in this plan; vision-tier-only, deferred.
