  - `async def run_pass1(text_sample: str, ontology: Ontology, llm: LLMExtractor) -> Pass1Output`.

    1. Build a compact schema representation (~500 tokens) using `Ontology.entity_types` names + descriptions.

### Phase B.1e — Multi-schema orchestrator (top-3 sequential + merge step)

**Goal**: tie B.1c + B.1d into a multi-schema pipeline. Run Pass 1 against top-3 applicable schemas sequentially; aggregate proposed extensions cumulatively; run Pass 2 once per schema; merge the three results into one `ExtractionResult` with multi-type tagging.

**Files to create**:

- `pipelines/ontology-extraction/src/ontology_extraction/multi_schema_orchestrator.py`:
  - `async def detect_applicable_schemas(source: Source, ontologies: List[Ontology], top_k: int = 3) -> List[Tuple[Ontology, float]]` — wraps the existing `document_mapper.get_ontology_for_document_type` + a (NEW) fallback heuristic that scores all available ontologies by entity-type name overlap with a quick keyword-extract from the document. Returns top-3 with confidence ≥ 0.3.
  - `async def run_multi_schema(source_id, chunks, applicable_schemas, llm, notebook_schema_repo, pass1_repo) -> ExtractionResult`. Algorithm per FEATURE_ROADMAP §621-639:
    1. For each `(schema, conf)` in top-3:
       1. Sample chunks (~1500 tokens).
       2. Call `run_pass1(sample, schema, llm)`.
       3. Persist a `pass1_results` row.
       4. Append `proposed_extensions` to a cumulative list (deduped by `type_name`).
    2. Soft-nudge decision (calculated, returned to caller — UI in B.3c presents it):
       - max coverage > 95% → silent (don't surface anything)
       - max coverage 80-95% → emit `notebook_event{type: "extension_suggested"}` row
       - max coverage < 80% → emit `notebook_event{type: "schema_mismatch"}` row
    3. For each schema sequentially: `run_pass2(chunks, schema, accepted_extensions_for_this_schema)`. Each pass returns an `ExtractionResult`.
    4. **Merge step** (in-process, no LLM):
       - Build a `(normalized_name) → MergedEntity` dict, where `MergedEntity` aggregates `type_tags: List[str]` from each pass, and `primary_type` is the label from the highest-confidence pass containing the entity.
       - Relations: dedup on `(source_text_normalized, target_text_normalized, relation_type)`, max-confidence wins.
       - Name normalization: import `from shared.utils.name_normalizer import normalize_entity_name` (NEW helper — see B.1f Open Q-B-7).
- `packages/shared/src/shared/utils/name_normalizer.py` — NEW. Stub implementation: `def normalize_entity_name(text: str) -> str: return re.sub(r'\s+', ' ', text.lower().strip().rstrip('.,;:')).strip()`. Single import point; Q9 (Track M4) replaces the body without changing the signature.
- `pipelines/ontology-extraction/tests/test_multi_schema_orchestrator.py` — extensive: 3 mock ontologies, 2 mock schemas applicable, merge correctness for entities present in 2-of-3 passes vs 1-of-3, relation dedup, name-normalization (`"  Foo Bar.  "` vs `"foo bar"`).

**Files to modify**:

- `pipelines/ontology-extraction/src/ontology_extraction/workflow.py` — `ExtractionWorkflow.extract(chunks)` becomes `extract(chunks, mode: Literal["single", "multi"] = "multi")`. In single-mode, current behavior preserved. In multi-mode, calls `run_multi_schema(...)`.
- `packages/shared/src/shared/models/extraction.py` — `ExtractedEntity` gains `type_tags: List[str] = Field(default_factory=list)` and `primary_type: Optional[str] = None`. Already has `confidence`.

**Acceptance criteria**:

1. With 3 mock ontologies and a synthetic document whose entities are split across 2 schemas, `run_multi_schema` produces a single `ExtractionResult` where each entity present in ≥ 2 passes has `type_tags` length ≥ 2 and `primary_type` matches the highest-confidence label.
2. Token budget per Pass 2 call ≤ 3000 tokens (perf guard, assert via prompt-token-count fixture; same threshold as B.1c).
3. `pass1_results` rows are written for each schema attempted.

## 4. Risk assessment

**Risk 1 — SCHEMAFULL migration cascades.** `entity` (migration 39) is SCHEMAFULL and is touched by B.1a (`type_tags`, `primary_type`) and B.5b (`orphan_status`, etc.). Adding fields is additive and safe via the IF NOT EXISTS pattern; renaming or removing is not. We will NOT rename any existing field. **Mitigation**: B.0 lands first; every later schema-touching PR runs the testcontainer roundtrip in CI before merge. **Severity**: medium-high.

**Risk 2 — Ollama context budget overruns in multi-schema mode.** With top-3 schemas and per-pass token budgets of 2000-3000 tokens, total per-source LLM cost is ~6× single-schema. With a 50-source notebook on a self-hosted llama3.1:8b, this could exceed practical processing time. **Mitigation**: B.1c and B.1e both have an explicit token-budget assertion in tests; the multi-schema flag is gated on `multi_schema_enabled: bool` (B.1f) for emergency rollback; we cap top-K at 3 (not 5+); the document detector confidence floor of 0.3 weeds out long-tail schemas before LLM cost is incurred. Telemetry from B.4 surfaces actual latency in production. **Severity**: medium.

**Risk 3 — Multi-schema merge correctness.** B.1e's merge step is the heart of multi-type tagging. Bugs here corrupt the KG silently — an entity with the wrong `primary_type` or a relation deduped to the wrong direction. **Mitigation**: B.1e ships with 12+ test fixtures including: same entity in 2 schemas with conflicting types, same entity name as 2 different real-world entities (NOT to be merged), entities differing only in whitespace, entities whose normalized names collide but should not (Q-B-4). The name-normalizer is a single import-point so Q9 can drop in proper logic without rewriting B.1e. **Severity**: medium-high.

**Risk 4 — Schema-edit → re-extract feedback loops.** A user edits a schema, B.3d prompts for re-extraction, the re-extraction triggers Pass 1 again, Pass 1 proposes new extensions (because schema has changed!), the soft-nudge fires again, the user accepts, B.3d prompts again. **Mitigation**: B.3d adds a `reextraction_in_progress: bool` guard on `NotebookSchema`; Pass 1's soft-nudge is suppressed when this flag is set; flag clears on completion. Also: in B.1e, when `accepted_extensions` already match the LLM's `proposed_extensions`, suppress the nudge. **Severity**: medium.

**Risk 5 — UI complexity for schema-tab editing.** The schema browser + edit dialog + soft-nudge + pause-toggle + reextract-prompt is a lot of UI surface in a small space. **Mitigation**: B.3a (view-only) ships before B.3b (edit); we validate the read flow before adding mutations. B.3c soft-nudge and B.3d reextract are separate PRs from B.3b. Each component is ~150-200 LOC and Playwright-tested in isolation. **Severity**: low-medium.

**Risk 6 — Orphan-connector LLM cost.** Each orphan can produce up to 3 candidate-partner proposals, each requiring an LLM confirmation call. A notebook with 200 orphans could trigger 600 LLM calls. **Mitigation**: B.5a config caps proposals per orphan at 3 (default; configurable); `orphan_connector_enabled` defaults to True but can be disabled per notebook; B.5b prune-lifecycle limits retries to 3 per entity. **Severity**: medium.

**Risk 7 — Cross-notebook merge entity-name collisions.** Two notebooks with `"Smith"` referring to different real people — merging would produce a corrupt entity. **Mitigation**: B.6's merge-by-`normalize_entity_name` is too aggressive on its own; we add a `type_match_required: bool = True` default that prevents merging entities with disjoint `type_tags`. Surfaces all collisions in the `NotebookMergeReport.conflicts` list for human review (Q-B-5). **Severity**: medium.

**Risk 8 — Pre-existing entity-persistence drift.** `entity_persistence_service.persist_filtered_result` writes fields that don't match migration 39 (names: `name`/`weight`/`source_ids` vs schema's `canonical_name`/`source_documents`). If SCHEMAFULL is enforced strictly, this is already broken; SurrealDB may be permissive enough to be quietly tolerating it. **Mitigation**: B.0 will surface this on roundtrip-test runs against the existing service. B.1a's PR explicitly fixes the drift (or documents it and triages — Q-B-1). **Severity**: medium (potentially already broken in main; B.0 reveals it).
