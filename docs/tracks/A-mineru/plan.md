#### Phase A.1c — Docling confidence metric + auto-fallback to MinerU

**Files to create**:

- `apps/app-main/src/app_main/services/parsing/confidence.py` — pure function `score_docling_extraction(result: IngestionResult) -> DoclingConfidenceScore` computing the 6-signal weighted score from the roadmap:

  | Signal | Weight | Computation source |
  |---|---|---|
  | OCR confidence avg | 0.30 | mean of `ExtractedElement.confidence` for `element.source == "ocr"` elements; 1.0 when no OCR ran |
  | Text density (chars/page) | 0.20 | `len(full_text) / max(1, page_count)`; normalize via `min(value / 1500, 1.0)` (1500 chars/page ≈ academic baseline) |
  | Heading detection rate | 0.15 | `count(elements where element_type in {TITLE, HEADING}) / page_count`; normalize via `min(value / 2.0, 1.0)` (≥2 headings/page = 1.0) |
  | Table parsing success | 0.15 | `1.0` if no tables present; else `count(tables with non-empty rows) / count(tables)` |
  | Image-to-text ratio | 0.10 | `1.0 - min(count(images) / max(1, count(text_elements)), 1.0)` — many images relative to text suggests scanned doc |
  | Unknown element_type % | 0.10 | `1.0 - (count(elements with type == TEXT and section_level == 0 and not bbox) / max(1, total_elements))` |

  Returns a dataclass `DoclingConfidenceScore(overall: float, signals: Dict[str, float], decision: Literal["accept", "fallback"], threshold: float)`. Pure function — no I/O, fully unit-testable.

- `apps/app-main/src/app_main/services/parsing/auto_fallback.py` — orchestrator wrapping the dual-extraction logic; lives in `SourceExtractor` namespace but extracted as a helper so it's testable in isolation. Public: `async def extract_with_auto_fallback(file_path, content_settings, docling_client, mineru_client, threshold) -> tuple[IngestionResult, str, DoclingConfidenceScore]` returning `(chosen_result, engine_used, confidence)`.

  Algorithm:
  1. Run docling → `docling_result`.
  2. If `not docling_result.success`: try MinerU; return MinerU result with `engine_used="mineru"`, `confidence.decision="fallback"`.
  3. Score docling result. If `confidence.overall >= threshold`: return docling, no fallback.
  4. Else: run MinerU. Return MinerU result with `engine_used="mineru"` (no comparative scoring of MinerU output — see Q-A-2).

- `apps/app-main/tests/test_docling_confidence.py` — table-driven tests with synthetic `IngestionResult` fixtures covering: high-quality native PDF (score > 0.95), scanned PDF with low OCR confidence (< 0.5), pure-image PDF (very low text density), table-heavy doc (high if rows populated, low if not).

- `apps/app-main/tests/test_auto_fallback.py` — cases: confidence above threshold ⇒ docling kept (mineru never called); confidence below ⇒ mineru called and returned; docling fails ⇒ mineru tried.

**Files to modify**:

- `packages/shared/src/shared/models/settings.py` (`ContentSettings`):
  - Add `docling_min_confidence: Optional[float] = Field(0.95, ge=0.0, le=1.0, description="Confidence threshold below which auto-mode falls back to MinerU")`.
- `frontend/src/lib/types/api.ts` — add `docling_min_confidence?: number`.
- `apps/app-main/src/app_main/services/source_extractor.py`:
  - In `_process_file`, when `parser_engine == "auto"`, replace the A.1b stub with a call to `extract_with_auto_fallback(...)`. Persist on `ExtractionResult.metadata`:
    - `parser_engine_used: "docling" | "mineru"`
    - `extraction_confidence: float` (overall score)
    - `extraction_confidence_signals: dict[str, float]`
    - `extraction_fallback_triggered: bool`
  - `SourceProcessor._update_source` already passes `extracted.metadata` through; verify it persists onto `Source.metadata` (the `metadata` dict on `ExtractedElement` is per-element — the Source-level metadata bag is the per-source dict `Source.metadata` via `_update_source`; if `Source` model doesn't have a top-level metadata dict at present, add one).

  **Note**: a `metadata: Dict[str, Any]` field exists on `Chunk` and `SourceInsight` but **not on `Source` itself** (see `packages/shared/src/shared/models/source.py` lines 107-131). We must either (a) add `metadata: Dict[str, Any] = Field(default_factory=dict)` to `Source` or (b) store extraction confidence on a sidecar table. Recommended (a) for simplicity — additive, non-breaking. Confirm in Open Question Q-A-3.
- `apps/app-main/src/app_main/api/routers/sources_processing.py` (`ReprocessRequest`):
  - Add `docling_min_confidence: Optional[float] = None`.

**Acceptance criteria**:

1. `score_docling_extraction()` returns a `DoclingConfidenceScore` with `overall` in `[0, 1]` for any input; weights sum to 1.0 (assert in test).
2. Synthetic "perfect document" fixture (high text density, good OCR, headings present, no unknown elements) scores ≥ 0.95.
3. Synthetic "scanned image-only" fixture (low text density, OCR confidence avg 0.4) scores ≤ 0.7.
4. With `parser_engine="auto"` and a fixture that scores 0.97, MinerU is **not** called (assert mock `MineruHttpClient.process` zero calls) and `metadata.parser_engine_used == "docling"`.
5. With `parser_engine="auto"` and a fixture that scores 0.60 (below default 0.95 threshold), MinerU **is** called and the returned result is the MinerU one; `metadata.extraction_fallback_triggered == True`.
6. With docling raising an exception, auto-mode swallows it, calls MinerU, returns MinerU result, logs at WARNING level.
7. Setting `processing_overrides.docling_min_confidence=0.99` on a reprocess request raises the bar for that one call (parametrized test).
8. `Source.metadata` after auto-extraction contains keys `parser_engine_used`, `extraction_confidence`, `extraction_confidence_signals`, `extraction_fallback_triggered` (verified via integration test against `TestClient`).
9. Total signal computation latency for a 50-page document fixture is < 50 ms (perf guard — score function must not become a bottleneck).

**Tests required**:

- Unit: `test_docling_confidence.py` (~10 fixtures covering signal-extreme cases).
- Unit: `test_auto_fallback.py` (4 paths above).
- Integration: extend `test_source_extractor.py` with one auto-fallback flow using mocked docling + mineru clients.

**PR boundary**: ONE PR titled `feat(ingestion): docling confidence-scoring + auto MinerU fallback (A.1c)`.

## 3. Risk assessment

**Risk 1 — GPU contention between docling and MinerU on a single GPU** | **Mitigation**: document the constraint in `services/mineru/README.md`; both services use lazy model loading (first request triggers download); auto-fallback runs the two parsers **sequentially** within one extraction call (never in parallel), so they never compete for VRAM. If users run both in production they need ≥ 12 GB VRAM; document. **Severity**: medium.

**Risk 2 — `mineru[all]` first-run download is large (~5-8 GB including PyTorch+Ray) and slow** | **Mitigation**: pre-pull at image build by adding `RUN python -c "import mineru; mineru.preload_models()"` to the Dockerfile **or** accept first-request latency and document it (preferred — keeps image small, lets users pick their GPU/model). Add a `model_cache` named volume in compose so models persist across container restarts. **Severity**: medium.

**Risk 3 — Confidence-metric calibration drift** — the 6-signal weighted score may not generalize beyond our pilot corpus. A user with mostly-scanned docs could see every doc fall through to MinerU (high cost, slow); a user with mostly-clean PDFs may see MinerU never trigger and wonder why the feature exists | **Mitigation**: ship with the default 0.95 threshold derived from Phase A.3 tuning; expose threshold in UI (already in plan); ship a CLI debug command `python -m app_main.scripts.score_extraction <source_id>` that prints per-signal scores so users can self-tune. Track usage telemetry post-launch (count of fallbacks per notebook per week) and revisit defaults at the M3-M4 boundary. **Severity**: medium.

**Risk 4 — Source.metadata field doesn't exist yet** (see Q-A-3) | **Mitigation**: adding it is additive and non-breaking; existing source records simply default to `metadata={}`; verify migrations are no-op via SurrealDB's permissive schema. If a migration is needed, ship it in A.1c PR. **Severity**: low.

**Risk 5 — MinerU output shape may not cleanly map to `ExtractedDocument`** — docling's HTTP service writes per-element JSON with bboxes/types/section_levels; MinerU's native output is markdown + a minimal JSON layout file. The client's `_load_document` may have to fabricate `ExtractedElement` instances or accept that MinerU sources have less rich element metadata, breaking downstream features that depend on `element_type` / `bbox` (e.g. PDF chunk viewer in `frontend/src/components/source/PdfChunkViewer.tsx`) | **Mitigation**: spike on this in Phase A.1a before committing to the HTTP-client design — if MinerU's JSON is too thin, surface as Q-A-5 below; worst case, MinerU output supports text-content viewing but **not** bbox-anchored PDF highlighting. Document the gap. **Severity**: medium-high (this is the biggest unknown).

**Risk 6 — Phase 3 refactor follow-ups + A2 confidence-scoring conflict with Track B4** | **Mitigation**: name the module `apps/app-main/src/app_main/services/parsing/confidence.py` (extraction-specific) and reserve `packages/shared/src/shared/utils/confidence.py` for a general scoring utility introduced by B4. The two compute different things — extraction confidence vs entity confidence — and live in different layers. **Severity**: low.

## 5. Open questions (escalate to user)

**Q-A-1 — Ephemeral venv vs baked-in install for MinerU?**
The roadmap §A1 step 1 says to install `mineru[all]` in **"an ephemeral uv-venv (overnemen van myKG's `src/mykg/uv_venv.py::ephemeral_mineru_venv`)"**. However, myKG uses ephemeral venvs because it's a CLI that runs once per invocation and avoids polluting the user's interpreter. We run as a **persistent FastAPI service inside a container**, so the rationale doesn't carry: we have a clean container, the `mineru[all]` install is large (~5-8 GB), and re-installing per call would dominate per-document latency. **Recommendation**: install once at image build (bake into the Dockerfile, mirror the docling pattern). The ephemeral-venv pattern is preserved as a documented option in `services/mineru/README.md` for users who want to swap MinerU versions without rebuilding. **Decision needed**: confirm the baked-in approach is acceptable, OR I implement the ephemeral path (cost: +1 day, +operational complexity, real benefit unclear).

**Q-A-2 — In auto-fallback mode, should we score the MinerU output too and pick the better result, OR always trust MinerU when docling falls below threshold?**
The roadmap snippet shows `select_best(docling_result, mineru_result)` which implies comparative scoring; but the scoring algorithm here is **calibrated for docling output** (e.g., `element.source == "ocr"` is docling-specific). Scoring MinerU output with the same algorithm would be apples-to-oranges. **Recommendation**: V1 = "trust MinerU when docling is below threshold" (no comparative score). V2 (future) = build an engine-agnostic scoring function. **Decision needed**: confirm V1 simplification.

**Q-A-3 — Does `Source` need a top-level `metadata` dict?**
`Chunk` and `SourceInsight` have one; `Source` does not (verified in `packages/shared/src/shared/models/source.py` lines 107-131). Phase A.1c plans to add `Source.metadata: Dict[str, Any]` to hold extraction confidence + engine used. **Decision needed**: (a) add it (additive, my recommendation), OR (b) extend the existing `Asset` model with a metadata bag, OR (c) create a new `source_extraction_meta` sidecar table. Option (a) is simplest and aligns with the pattern on sibling models.

**Q-A-4 — Playwright E2E: where does it live and is the runtime already wired?**
The codebase has no `playwright.config.ts`, no `@playwright/test` in `frontend/package.json`, and no `apps/app-main/tests/e2e/` directory. Adding Playwright for the first time is a meaningful tooling expansion (CI changes, dependency footprint, ~1 day to wire up). **Recommendation**: V1 ships with the manual QA checklist (`MANUAL_QA.md`); Playwright E2E is split into a separate tooling-track task to avoid bundling tooling adoption with feature delivery. **Decision needed**: confirm manual-QA-only for V1, OR allocate +1 day in Phase A.3 to introduce Playwright (likely with consequences for Track G testing too).

**Q-A-5 — MinerU output schema gap may break PDF highlighting**
If MinerU's native JSON output lacks per-element bounding boxes (it produces markdown + a minimal layout file), then `PdfChunkViewer` will not be able to highlight chunks for MinerU-parsed sources (it relies on `ExtractedElement.bbox`). The plan must either: (a) write a layout-to-bbox parser inside `MineruHttpClient` (effort: +0.5-1 day, depends on what MinerU emits), or (b) accept that MinerU-parsed sources show text-only chunks without PDF highlighting (UX regression vs docling). **Decision needed**: spike in Phase A.1a to determine which of (a)/(b) applies; this question may be answerable mechanically once we run MinerU once, but it's a real V1 scope question.

**Q-A-6 — Naming clash with existing `default_content_processing_engine_doc`**
We are adding `parser_engine` next to the existing `default_content_processing_engine_doc` (values: `auto`, `docling`, `simple`). The semantics are different — the old field gates **whether** docling-class processing runs vs "simple" extraction, while `parser_engine` gates **which** parser runs when docling-class is selected. But users may find this confusing in the Settings form. **Decision needed**: (a) keep both fields as proposed (with clear UI labelling — my recommendation), OR (b) extend the existing enum to `auto/docling/mineru/auto-mineru/simple` (more compact but mixes orthogonal concerns), OR (c) rename one of them in a single coordinated migration (more cleanup, more risk).
